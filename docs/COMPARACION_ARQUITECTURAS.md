# Comparación de Arquitecturas: Hexagonal vs. En Capas

Este documento presenta una comparativa técnica y pedagógica detallada entre las dos implementaciones del backend del sistema de **Triaje de Salud Mental**:
1. **Backend Hexagonal (`backend/`)**: Basado en Puertos y Adaptadores (Arquitectura Limpia / Onion Architecture).
2. **Backend en Capas (`backend-capas/`)**: Basado en la arquitectura clásica de capas del curso (Modelo, Repositorio, Servicio, Controlador, Dto, Mapper, Regla, Seguridad, Tarea) con convenciones de nombres por prefijo (`M...`, `I...`, `S...`, `C...`).

Ambos backends cumplen estrictamente el mismo contrato HTTP (`docs/CONTRATO_API.md`), de modo que el **frontend (`frontend/`) interactúa de forma idéntica e indistinta** con cualquiera de las dos implementaciones sin requerir una sola línea de cambio.

## 1. Tabla Comparativa General

| Criterio | Backend Hexagonal (`backend/`) | Backend en Capas (`backend-capas/`) |
| :--- | :--- | :--- |
| **Estructura de paquetes** | Organizado por intención y límites arquitectónicos:<br>• `dominio/` (modelo, eventos, reglas, excepciones)<br>• `aplicacion/` (casos de uso, puertos de entrada/salida, DTOs)<br>• `infraestructura/` (adaptadores web, persistencia JPA, seguridad, tareas, reportes) | Organizado por rol de capas tecnológicas:<br>• `Modelo/` (entidades `M...`)<br>• `Repositorio/` (interfaces `I...`)<br>• `Servicio/` (lógica de orquestación `S...`)<br>• `Controlador/` (endpoints REST `C...`)<br>• `Dto/` (records de transferencia)<br>• `Mapper/` (interfaces MapStruct `I...Mapper`)<br>• `Regla/` (políticas y reglas puras)<br>• `Seguridad/` (JWT, filtros, rate limiter)<br>• `Tarea/` (jobs programados y runners) |
| **Flujo de dependencias** | **Inversión de Dependencias (DIP)** estricta:<br>La infraestructura depende de la aplicación; la aplicación depende del dominio; el dominio no depende de ningún framework ni biblioteca externa. | **Flujo Descendente Clásico**:<br>`Controlador` $\rightarrow$ `Servicio` $\rightarrow$ `Repositorio` / `Modelo`. Los servicios y repositorios conocen directamente las anotaciones de Spring y JPA/Hibernate. |
| **Persistencia y Entidades** | **Separación total**: Los objetos de dominio (`Usuario`, `Evaluacion`, etc.) son POJOs/Records inmutables puros. La persistencia tiene sus propias clases `...Entidad` mapeadas con JPA y adaptadores de repositorio que traducen entre dominio y persistencia. | **Entidades como Modelo Central**: Las entidades `M...` (`MUsuario`, `MEvaluacion`, etc.) conviven con las anotaciones `@Entity`, `@Table`, `@ManyToOne` y son manipuladas directamente por los repositorios `JpaRepository`. |
| **DTOs y Transformación** | Mapeo manual mediante constructores y métodos de fábrica estáticos (ej. `RespuestaUsuario.desde(usuario)`). | Uso de **MapStruct** con interfaces `@Mapper(componentModel = "spring")` (`IUsuarioMapper`, `IEvaluacionMapper`, etc.) que generan el código de transformación en tiempo de compilación. |
| **Lógica de Negocio** | Dividida entre:<br>• *Reglas de Negocio Puras*: En entidades y servicios de dominio (`dominio/modelo/`).<br>• *Casos de Uso*: Clases de orquestación transaccional individuales con un solo método `ejecutar()` (`aplicacion/casouso/`). | Centralizada en:<br>• *Servicios Cohesivos (`Servicio/S...`)*: Agrupan múltiples operaciones de un mismo dominio funcional (ej. `SAutenticacion`, `SEvaluacion`, `SCita`).<br>• *Paquete `Regla/`*: Clases utilitarias de lógica pura independientes de framework. |
| **Gestión de Base de Datos** | **Flyway obligatorio**: Control estricto de migraciones mediante scripts SQL numerados (`V1__...sql` a `V6__...sql`). Requiere MySQL Community 8.0 o Docker. | **Hibernate DDL Automático**: `spring.jpa.hibernate.ddl-auto=update` sin Flyway. Diseñado para funcionar nativamente con **MariaDB de XAMPP (puerto 3306)** o cualquier MySQL local sin pasos manuales de migración. |
| **Pruebas Automatizadas** | Pruebas de integración con **Testcontainers** y Docker real (requiere Docker Desktop encendido). | Pruebas de integración con **H2 en modo MySQL** (`MODE=MySQL`) en memoria, eliminando la dependencia de Docker para integración continua y ejecución ágil en cualquier máquina de desarrollo. |
| **Ventajas** | • Máxima independencia del framework y de la base de datos.<br>• Alta testabilidad con mocks puros sin cargar el contexto de Spring.<br>• Mantenibilidad superior en sistemas empresariales masivos o con múltiples canales (web, consola, eventos). | • Estructura intuitiva, rápida de navegar y muy extendida en la industria Java/Spring Boot.<br>• Menor cantidad de clases puente y adaptadores (reduce el *boilerplate*).<br>• Desarrollo y refactorización más ágiles para equipos estándar y proyectos académicos.<br>• Integración transparente con MapStruct y Spring Data JPA. |
| **Desventajas** | • Mayor cantidad de archivos y capas puente (puerto $\rightarrow$ adaptador $\rightarrow$ entidad $\rightarrow$ modelo).<br>• Curva de aprendizaje más pronunciada.<br>• Requiere disciplina estricta para no contaminar el dominio con anotaciones de Spring o Jackson. | • Acoplamiento de las entidades `M...` con el framework JPA/Hibernate.<br>• Si el servicio crece desordenadamente, puede tender a convertirse en una clase con demasiadas responsabilidades si no se divide adecuadamente. |

## 3. Conclusión Pedagógica

- La **Arquitectura Hexagonal (`backend/`)** es excelente para comprender la inversión de control, la segregación de interfaces y cómo blindar el núcleo de negocio de cualquier acoplamiento tecnológico.
- La **Arquitectura en Capas (`backend-capas/`)** provee una aproximación directa y pragmática ampliamente utilizada en proyectos empresariales Spring Boot, optimizada para interactuar fluidamente con **XAMPP / MariaDB**, frameworks de mapeo como **MapStruct** y pruebas de integración rápidas en **H2**.
